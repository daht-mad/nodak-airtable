# 관계형 DB 설계 인터뷰

사람이 "DB 설계해줘", "에어테이블 만들어줘", "표 짜줘"라고 하거나, 연결 직후 베이스가 비어 있으면 이 인터뷰를 한다.
**바로 테이블부터 만들지 않는다.** 엑셀 한 장에 다 몰아넣는 "평평한 표"가 되기 때문이다.

목표: 사람의 **업무(도메인)** 를 듣고 → 테이블 여러 개 + 테이블끼리 **링크**로 이어진 구조를 같이 정하고 → 확인받은 뒤 만든다.

## 진행 원칙

- **한 번에 질문 1~2개.** 설문지처럼 10개를 던지지 않는다.
- 사람 말로 묻는다. "엔티티", "카디널리티", "정규화" 같은 단어를 질문에 쓰지 않는다. 설명이 필요하면 쓰고 바로 풀어준다.
- 사람이 예시를 들면 그 예시로 다음 질문을 만든다.
- 각 단계 끝에 지금까지 정한 걸 3줄 이내로 되짚는다.

## 1단계 — 일 듣기 (무엇을 기록하나)

- "이 표로 어떤 일을 관리하고 싶어? 요즘 손으로 하는 거 하나만 말해줘."
- "지금은 그거 어디에 적고 있어? (엑셀·노트·카톡·머릿속)"
- "그 기록 보고 제일 자주 하는 질문이 뭐야? 예: '이번 달 안 낸 사람 누구지?'"
  → 이 질문이 나중에 **뷰·필터**가 된다. 메모해 둔다.

## 2단계 — 명사 뽑기 (테이블 후보)

- 사람이 한 말에서 **반복해서 나오는 명사**를 뽑아 보여준다. 예: 독서모임 → 회원, 모임, 책, 출석
- "이 중에 **각각 따로 목록이 있어야** 하는 게 뭐야?"
- 판단 기준 — 이런 건 **별도 테이블**:
  - 그것만의 정보가 여러 개 있다 (회원 = 이름·연락처·가입일)
  - 같은 값이 여러 줄에 반복해서 적힌다 (출석표마다 회원 이름·연락처를 또 적고 있다)
- 이런 건 **그냥 칸(필드)**: 하나의 값이고 따로 관리할 정보가 없다 (상태: 진행중/완료 → 단일 선택)

## 3단계 — 관계 묻기 (링크)

테이블 후보 두 개씩 짝지어 묻는다:

- "회원 한 명이 모임에 **여러 번** 올 수 있어? 모임 하나엔 회원이 **여러 명** 와?"
  - 한쪽만 여럿 (1:N) → 링크 칸 하나로 끝. 예: 책 1권 ← 모임 여러 번
  - 양쪽 다 여럿 (N:M) → **중간 테이블**을 제안한다. 예: 회원 ↔ 모임 → `출석` 테이블 (회원 링크 + 모임 링크 + 출석 여부·메모)
    - "출석할 때 같이 적고 싶은 게 있어? (지각·메모·후기)" — 있으면 중간 테이블이 확실히 필요하다.
- 사람이 "그냥 이름 적으면 안 돼?"라고 하면 이유를 하나만 든다:
  이름을 텍스트로 적으면 오타·동명이인으로 갈라지고, 연락처가 바뀌면 모든 줄을 고쳐야 한다. 링크면 한 곳만 고치면 된다.

## 4단계 — 칸 정하기 (필드)

테이블마다:

- **첫 칸(Primary)** = 그 줄을 한눈에 알아보는 이름. 사람이 목록에서 고를 때 보이는 값이다. (회원 → 이름, 모임 → `10/7 모임`)
- 나머지 칸은 타입까지 같이 정한다. 자주 쓰는 것:
  | 이럴 때 | 타입 |
  |---|---|
  | 짧은 글 | `singleLineText` |
  | 긴 메모 | `multilineText` |
  | 정해진 보기 중 하나 | `singleSelect` |
  | 날짜 | `date` |
  | 숫자·금액 | `number` / `currency` |
  | 체크 | `checkbox` |
  | 다른 테이블과 연결 | `multipleRecordLinks` |
- 링크 건너편 값을 보여주고 싶으면 **룩업(lookup)**, 세고 더하려면 **롤업(rollup)/카운트**. 예: 회원 테이블에 "출석 횟수" = 출석 링크 카운트
- **같은 정보를 두 테이블에 텍스트로 복사하지 않는다.** 필요하면 링크 + 룩업.

## 5단계 — 설계안 확인

만들기 전에 이 형식으로 보여주고 **"이대로 만들까?"** 를 묻는다:

```
📋 독서모임 운영 — 테이블 4개

회원: 이름 · 연락처 · 가입일 · 출석(→출석) · 출석 횟수(카운트)
책:   제목 · 저자 · 모임(→모임)
모임: 이름 · 날짜 · 책(→책) · 출석(→출석)
출석: 이름 · 회원(→회원) · 모임(→모임) · 왔나(체크) · 한 줄 후기

자주 볼 질문 → 뷰
- "이번 모임 안 온 사람" → 출석 테이블, 왔나=꺼짐 필터
```

`(→테이블)` = 링크 칸. 그림이 더 잘 보이는 채널이면 관계도를 그려도 된다.

## 6단계 — 만들기 (승인 후에만)

순서가 중요하다. **링크 칸은 상대 테이블이 있어야 만들 수 있다.**

1. 링크 없이 테이블부터 전부 만든다 — `create-table.ts` (첫 칸 + 일반 칸만)
2. `sync-schema.ts`로 새 테이블 ID를 받는다 (`tbl...`)
3. 링크 칸을 추가한다 — `create-field.ts`
   ```json
   {"name":"회원","type":"multipleRecordLinks","options":{"linkedTableId":"tblXXXXXXXXXXXXXX"}}
   ```
   만든 뒤 `sync-schema.ts`로 건너편 테이블에 반대 방향 링크 칸이 생겼는지 본다. 생겼으면 따로 만들지 않는다.
4. 룩업은 링크가 생긴 뒤 API로 추가할 수 있다:
   ```json
   {"name":"회원 연락처","type":"multipleLookupValues","options":{"recordLinkFieldId":"fldLINK","fieldIdInLinkedTable":"fldTARGET"}}
   ```
   카운트·롤업·수식은 API 문서상 옵션이 읽기 전용이라 실패할 수 있다. 실패하면 우회하지 말고 "이 칸은 에어테이블 화면에서 만들어줘"라고 칸 이름·설정을 적어서 안내한다.
5. 예시 데이터 2~3줄을 넣어서 링크가 실제로 이어지는지 보여준다.
6. 다시 `sync-schema.ts` → 최종 구조를 한 번 더 보여준다.

## 끝나고 남길 것

- 정한 설계안(5단계 형식)을 사람에게 한 번 더 주고, 봇 자신의 기록 파일에도 남긴다 — 다음 대화에서 "그 표 어떻게 생겼지?"를 다시 묻지 않게.
- 1단계에서 받은 "자주 하는 질문"이 이제 표로 답이 되는지 하나 골라 직접 조회해 보여준다.
